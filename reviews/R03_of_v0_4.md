# Review of Agentic Economics v0.4 and its reference implementation

**Basis:** the uploaded v0.4 specification, its explicitly inherited v0.3/v0.2/v0.1 rules, and the eleven supplied source/test/README files. No outside research was used. This is a protocol-conformance and executable-regression review, not a run of economic strategies or a security audit of deployed software.

## Results and reproduction

I reconstructed the supplied directory structure. All original files in `agentic_sim/` remain byte-identical to the uploads; `results/source_manifest.json` records their SHA-256 hashes.

| Run | Result |
|---|---|
| Supplied plain-Python runner | 23 passed, 0 failed |
| Supplied tests under pytest | 23 passed |
| Independent, targeted regression cases | 20 failed |

The additional cases were deliberately chosen to test uncovered boundary conditions. Their failure rate is **not** an estimate of the failure rate in ordinary operation, and twenty cases do not mean twenty independent root causes. One case specifically exposes an assessment outcome that the API cannot express; it needs a representation/rule clarification rather than simply a different comparison operator.

Run from `agentic_sim/`:

```sh
python run_tests.py
python -m pytest tests/test_spec.py -q
python -m pytest tests/test_review_regressions.py -q --tb=short
python review_observations.py
```

The additional suite requires pytest. The original `run_tests.py` remains unchanged and discovers only the supplied `test_spec` module. `review_observations.py` also imports the added test helpers and therefore requires pytest. Environment: Python 3.13.5, pytest 9.0.2. Full outputs are in `results/`.

Most new tests suppress emission and service fees to isolate state transitions; the fee-shortfall tests enable service fees and start with an empty operating float. The dilution tests produce emission through a normally settled prior case, using the same large-emission stress approach already present in the supplied suite. All new fixtures enable the reserve invariant. These are documented parameter choices, not proposed economic defaults.

## Overall assessment

The supplied examples genuinely run. The revised haircut formula, ordinary bond-funded appeal, inclusive challenge boundary, and normal nested-contract path are now executable rather than prose-only.

The main remaining problem is **reference-implementation conformance**. Several ordinary exceptional paths differ from the selected rules. In addition, some of the implemented invariant predicates are substantially weaker than their descriptive names. Passing them is useful but does not demonstrate all of the corresponding promises.

This does not require a new economic architecture. It requires repairing transitions, preserving money units, implementing already-selected mechanisms, and extending regression coverage before using strategy outcomes as evidence about the economy.

## A. Invalid operations can alter finances

**Source:** `sim/engine.py:238–276, 491–502`; `sim/ledger.py:145–166`; `sim/invariants.py:26–47`.

### Negative and nonfinite purchases

`World.spend('A', -10)` succeeds. It adds ten credits to A, ten to the recorded reserve, and ten to supply, while recording an ordinary `purchase` event. All existing invariant checks pass.

`World.spend('A', float('nan'))` also succeeds. Wallet, reserve and supply become NaN; all existing checks again pass. Comparisons such as `abs(total - M) > EPS` and `U < -EPS` do not reject NaN.

This is an input-validation problem, not an economically legitimate strategy. A rule engine receiving injected actions must reject such input. Values that represent cost, price, duration, balances and quantities need explicit domain/finite-value validation at their boundaries. The simulation's external actor policies are not a substitute for the promised action validation.

### Partial award after an exception

A requester with 42 credits can afford a price of 40 but not the ten-credit verification deposit. `award()` locks A's 20-credit guarantee, moves 40 credits into escrow, and then raises when funding the deposit fails. The case remains `AVAILABLE`, A has no recorded ordinary commitment, yet the funds have moved. All existing invariant checks pass.

Similarly, `_open_challenge()` sets `challenge_round_used=True` before trying to collect the fee. If collection fails, the case has consumed its appeal round without creating a challenge.

The financial action should either complete under its rules or leave financial obligations unchanged. Recording an unsuccessful attempt in history is compatible with that requirement; partially executing the attempted transaction is not.

**Regression cases:** 14, 15, 16 (negative and NaN).

## B. Reviewer occupation is not represented

**Source:** `sim/engine.py:39–52, 301–325`; `sim/invariants.py:148–172`. Spec: v0.4 §12 plus inherited one-active-assignment and review-capacity rules.

The same duty actor can receive two unfinished reviews on separate cases at the same time. `_eligible()` checks duty membership, exclusions and unlocked balance, but not an existing active review or ordinary commitment. I14 examines ordinary commitments only.

A completed review retaining financial liability is supposed to differ from an unfinished review retaining execution occupancy. The implementation currently does not enforce the latter. This directly changes the opportunity cost and reserve behavior the economy is intended to study.

**Observed:** C assigned both `r1` and `r2`, both `open`, with all existing checks passing.

**Regression case:** 01.

## C. Timeout replacement works only for initial reviews

**Source:** `sim/engine.py:340–365, 491–502, 526–547, 847–854`. Spec: v0.4 §7.5 and §12.

`_withdraw_review()` changes the review status and handles the bond but does not remove the old reference from the challenge's review list or repair its suspension bookkeeping.

An appeal with one completed review and one timed-out review cannot appoint a replacement: `assign_appeal()` sees two historical entries and rejects the action.

A timed-out audit also cannot be replaced: `assign_audit()` rejects any case with any historical audit. The case's `open_items` remains nonzero. Releasing the timed-out review's capacity does not release or replace its case-level obligation.

The existing test exercises an **initial** reviewer timeout followed by a replacement, then a successful audit/appeal. It does not exercise the two failing replacement paths.

The fix must distinguish replacing an already opened position from opening a new audit or a second challenge round. It should also preserve the original timely admission when a replacement is needed after the nominal challenge window.

**Regression cases:** 02 and 03.

## D. Prices float, but review-cost units do not

**Source:** `sim/engine.py:368–408`; `sim/ledger.py:145–166`. Spec: v0.4 §4.3–§4.5 and §7.3.

`complete_review(..., cost)` sends `cost` to `Ledger.purchase()`, where it is a real-unit cost converted into credits. The returned credit expenditure is discarded. The same raw number is then stored in `r.cost` and compared against `c.K`, a cap denominated in credits.

**Observed stress case:** after a prior case's emission, one credit is worth approximately 0.5 real units. A new review spends three real units, costing approximately six credits. Its indexed cap is approximately ten credits. It is reimbursed three credits, rather than approximately six.

The bug can be numerically invisible in a test where one credit equals one real unit. Under changing prices, it distorts reimbursements, excess-cost margins, deposit depletion and operating-account advances.

A further cost-attribution issue affects nested cancellation. `actor_cost` accumulates direct resource spend and some kill fees but not a completed subcontract's delivery payment. In the regression, B has paid G two credits for completed work; when A cancels B before B submits, B receives a zero kill fee. The specification says execution cost includes nested payments. If an additional eligibility exclusion is intended, it needs to be stated rather than inferred from this omission.

**Regression cases:** 04 and 17.

## E. Nested rejection collateral is not reconciled at award

**Source:** `sim/engine.py:207–221, 251–273, 598–610`. Spec: v0.4 §4.5 and §9.2.

Posting a nested request locks a rejection bond at the current credit index. Awarding it later recalculates `D`, `K` and `G_V` using the award-time index, but leaves `rejection_bond` at its posting-time amount.

**Observed:** a bond of five credits is locked at posting. Another case vests and dilutes the currency. The nested case is awarded with `G_V` approximately ten; its actual rejection bond is still five.

Thus the corrected rule fixes late-assigned ordinary reviewers but not the interval between a nested request's posting and award. Sufficient movement can also make the court fee exceed the actual rejection bond. The aggregate locked wallet can conceal the problem by containing unrelated delivery collateral.

Reconciliation must apply one specified valuation basis to the promised liability and its actual lock. The case needs to remain affordable if an award requires additional collateral.

**Regression case:** 05.

## F. Deferred reimbursements are recorded but not fully serviced

**Source:** `sim/engine.py:164, 368–391, 748–797` and service-fee collection at `238–276`. Spec: v0.4 §4.3 and §10.4.

### FIFO debt never pays

The engine appends to `omega_claims` but has no code that drains the list when later service fees arrive.

**Observed:** a settled reviewer has a 2.5-credit claim. A new award puts three service-fee credits into Ω. After advancing time, the reviewer has received zero additional credits and the claim remains unchanged.

### Deferred cost of an overturned reviewer disappears from the payable queue

`_settle_reviews()` processes deferred reimbursements only for surviving reviews. An overturned reviewer can have valid, capped but unpaid costs from its completed review. Its fee should not vest, and it loses its bond, but the specified reimbursement obligation has not been cancelled by either rule.

**Observed:** 2.5 of five eligible credits is reimbursed; 2.5 remains in the overturned review's `deferred` field and never becomes an Ω claim. Surviving reviews settle normally.

### No-review deposit goes to Ω

On the exposed path where a human explicitly overrides a submitted result to F before any paid review, the case settles without an entitled reviewer. `_settle_reviews()` labels the entire unused ten-credit deposit a pool-sweep residue and sends it to Ω, rather than returning it to the requester.

These are payout/obligation handling defects, not evidence that the chosen reimbursement policy is economically unsound.

**Regression cases:** 06, 07 and 18.

## G. Human overrides do not consistently update dependent outcomes

**Source:** `sim/engine.py:697–725, 748–806`; spec v0.4 §15, inherited v0.3 §15.2.

An override uses a separate settlement path from a dispute and does not consistently reconcile reviewers.

**Before vesting:** C approves a result at cost three; the human changes the outcome to N. The actor forfeits its guarantee. C nevertheless vests, receives the seven-credit deposit residue as a fee in the zero-emission fixture, regains its bond, and gains reliability/duty credit. The review is now positively rewarded despite being contradicted by the final ruling. All existing checks pass.

**After vesting:** no clawback is correctly performed, but only the delivery actor receives an adverse reliability update. The involved reviewer remains credited as successful, contrary to the inherited override rule concerning actor and reviewers.

**Nested override:** the override method assigns `human-explicit` directly to a finalized nested case, while the specification and I13 require all nested cases to be procedural. The label is inconsistent before the next invariant check, which would then fail.

These paths should share the selected semantics for final assessment, reviewer responsibility, grades and financial finality, rather than implementing unrelated partial versions of them.

**Regression cases:** 08, 09 and 10.

## H. Partial fulfillment and missing evidence need their own state semantics

**Source:** `sim/engine.py:393–414, 452–481, 560–580`; `sim/params.py:9–13`. Spec: v0.4 §3, §6, inherited v0.2 §6.

**Partial revision:** the code accepts another P after the actor has already used its one allowed revision. It has no revision-count field or restriction requiring the re-review to return F or N. `T_rev` and `T_evid` exist in parameters but are never read by the engine; the only response deadline is `T_resp`. A driver currently cannot represent the full two-stage choice/work timing expressed by the inherited windows.

**Appealing BOT:** every completed appeal returns F or N. Both strings differ from the original BOT string. `_settle_challenge()` therefore always treats the original missing-evidence claim as overturned, always penalizes its author, and reimburses the actor's appeal fee — even when the final task outcome is N.

The required branch is not expressible: “the missing evidence really was missing; the objection is rejected.” Conversely, a missing-evidence claim could be wrong while the result still fails for another reason. Therefore simply changing the code to treat every final N as an upheld BOT would be an unjustified new rule. The representation needs to distinguish disposition of the objection from the task's final fulfillment outcome, or otherwise explicitly encode the chosen semantics.

Regression 12 encodes the intended upheld-evidence-failure case. Its failure documents this representational gap; it is not a claim that every N following BOT must leave the original review unpenalized.

**Regression cases:** 11 and 12. Missing window use also confirmed by source inspection.

## I. One failure exit still leaves orphaned sibling requests

**Source:** `sim/engine.py:645–687`. Spec: v0.4 §9.4 / R54.

Normal `_finalize_N()` withdraws the failed parent's unawarded children. `withdraw_pool_exhaustion()` implements its own final-N transition and withdraws only the triggering child.

**Observed:** A has two unawarded children. After reduced-forfeiture withdrawal caused by the first, the parent is final N, the second child remains AVAILABLE, and six credits remain locked. All existing checks pass.

The new orphan-cleanup rule is sound; it must run on each relevant terminal path. A similar inspection is warranted for cancellation at deeper levels, rather than assuming the ordinary finalize method covers every exit.

**Regression case:** 13.

## J. Several specified mechanisms are not implemented by this skeleton

These are scope gaps, distinct from incorrect transitions.

- **Rotation:** `engine.py:12` explicitly says rotation is not modeled. There is no reserve-handover operation. The selected three-review/30-tick duty rule and incoming/outgoing selection require an implementation or an explicit harness responsibility.
- **Reserve initialization/enforcement:** `on_duty` defaults to an empty list and `enforce_reserve` defaults to false; the prescribed lowest-ID reserve is not constructed by default. The additional tests supply a valid reserve and enable enforcement, so the failures above do not depend on this default.
- **Rolling reputation and duty windows:** `s`, `o`, and `kappa` are cumulative counters. The inherited 100-outcome reliability and 100-tick duty-credit windows are not implemented. The regression verifies that a review still contributes duty credit at tick 112 after vesting at tick 10.
- **Audit blindness:** a policy receives the full `world` and review ID; review role, other verdicts and identities are accessible. No filtered observation interface implements the specified view. Ordering an audit after a verdict is not the same as hiding that verdict.
- **Committed history:** case logs and ledger events are ordinary mutable in-memory objects, without the cryptographic commitments discussed in the broader project. A lightweight deterministic harness need not implement production cryptography, but its scope must distinguish stored events from demonstrated tamper-evidence.
- **Economic strategies, learned selection, and actual evaluator behavior:** deliberately absent, as the README states. Their absence is not itself a defect in a rules-only harness. It means the supplied pass count is not evidence about incentives, verification quality, learning or performance under market load.

**Regression case:** 19 covers duty-credit expiry; the other items are source-scope findings.

## Why the invariant checks do not catch these cases

The checks are useful initial assertions, not an exhaustive formal specification.

I1 checks aggregate credit balance, not whether an otherwise conserving payment was authorized. I3 checks an event-kind whitelist, not signed amounts or a reconstruction of authorized mint/burn quantities. I14 checks the ordinary `committed` field, not simultaneous reviews. I12 snapshots on its first check rather than at award. I15 counts aggregate reviewer locks but does not reconcile every delivery guarantee against a distinct lock record. I13 validates the grade vocabulary and the nested exception, not the provenance of each grade.

`results/review_observations.json` demonstrates six problematic states that the current full check set accepts: overlapping reviews, a negative purchase, a NaN purchase, a partly executed failed award, an overruled-but-rewarded review, and an orphaned nested request.

An invariant passing says the implemented predicate returned successfully. It does not make the predicate's descriptive name true in all its intended meanings.

## Recommended scope of the next pass

Do not add more economic mechanisms just to repair these findings. First make invalid actions safe, track execution occupancy, fix replacement references, preserve currency units and liabilities, and make all settlement paths apply the same obligations. Clarify the missing-evidence appeal representation and the posting/award denomination boundary explicitly. Then implement or clearly bracket the selected scheduling, observation and history features.

Re-run both the original examples and the added regressions. Only then do strategy-driven runs supply interpretable evidence about the stated economic hypotheses. The appropriate claim today is that **the scripted examples execute, and independent executable checks have identified additional protocol-conformance work** — not that the economy is disproven, nor that passing the original suite established complete conformance.
